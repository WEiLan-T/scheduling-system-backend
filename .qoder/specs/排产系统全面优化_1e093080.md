# 排产系统全面优化方案

## 现状分析

- **排产引擎**：`EstimationService.previewSchedule()` 仅支持单订单排产，不感知已有排产的资源占用，`findMaxWeavingEndDate`/`findMaxCoexEndDate` 虽已定义但未用于冲突检测
- **订单甘特图**：`orderGanttRows`（app.js:830-867）仅展示 orderDate→deliveryDate，不显示排产引擎计算的实际计划日期；甘特条不可点击
- **数据断层**：排产结果（`EstimatedProductionSchedule`）与执行层（`WeavingDailyLog`/`CoexDailyLog`）无数据回流闭环
- **前端架构**：app.js 950行单文件，菜单9项分3组，登录时一次性加载所有数据

## 核心策略

增量改造 — 新增接口/方法/面板，不拆分 `DataEntryService`，不重构 `app.js` 整体结构。排产并发用贪心算法（按交货期紧→松排序），不回溯。

## 阶段一：多订单并发排产引擎

### Task 1 — 新增多订单排产请求 DTO
- **文件**：新建 `src/main/java/com/company/scheduling/dto/MultiOrderScheduleRequest.java`
- **内容**：包含 `List<String> orderIds`、`Integer globalBufferDays`、`Integer weavingAdvanceDays`、`List<ItemAdjustment> itemAdjustments`
- **依赖**：无

### Task 2 — EstimationService 新增多订单并发排产方法
- **文件**：`src/main/java/com/company/scheduling/service/EstimationService.java`
- **方法**：`previewMultiOrderSchedule(MultiOrderScheduleRequest req, String currentUser)`
- **核心逻辑**：
  1. 按交货期从紧到松排序所有订单（贪心优先级）
  2. 维护 `Map<String, LocalDateTime>` 机台/产线占用时间线（resourceTimeline）
  3. 对每个订单复用现有 `previewSchedule` 的单订单逻辑，但在分配机台时检查 resourceTimeline 避免冲突
  4. 利用已有 `findMaxWeavingEndDate`/`findMaxCoexEndDate` 初始化时间线
  5. 新订单的排产开始时间 = max(当前时间, 该机台/产线已有排产的结束时间)
- **依赖**：Task 1

### Task 3 — EstimatedProductionScheduleRepo 新增占用查询
- **文件**：`src/main/java/com/company/scheduling/repository/EstimatedProductionScheduleRepo.java`
- **新增方法**：
  - `findByWeavingMachineIdAndWeavingEndDateAfter(String machineId, LocalDateTime after)` — 查询某机台未来被占用的时段
  - `findByCoexLineIdAndCoexEndDateAfter(String lineId, LocalDateTime after)` — 查询某产线未来被占用的时段
  - `findByOrderId(String orderId)` — 按订单号查询排产记录（后续阶段需要）
- **依赖**：无

### Task 4 — EstimationController 新增多订单排产端点
- **文件**：`src/main/java/com/company/scheduling/controller/EstimationController.java`
- **新增**：`@PostMapping("/preview-multi")` 接收 `MultiOrderScheduleRequest`
- **依赖**：Task 2, Task 3

## 风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 多订单并发排产资源争用逻辑复杂 | 高 | 贪心顺序排产（按交货期紧→松），不做回溯优化 |
| DataEntryService 601行巨型类改造回归 | 高 | 不拆分，仅通过新增方法扩展 |
| app.js 950行修改引入 bug | 中 | 增量添加函数和 ref，不重构现有代码结构 |
| ddl-auto:update 导致 Schema 不一致 | 中 | 所有新字段允许 NULL 或有默认值 |
| 前端一次性加载数据量大 | 低 | 阶段四改为按需加载 |
| 排产-执行对比查询性能 | 低 | 查询条件限定 orderId + 日期范围，索引覆盖 |

## 废弃方案说明

- **DataEntryService 拆分**：虽然该类职责过多（织造/共挤/库存/工艺），但拆分涉及 Controller 注入变更和前端 API 路径调整，回归风险过高，采用新增方法扩展策略
- **app.js 组件化重构**：950行单文件确实应拆分为多个模块，但全量重构工作量巨大且风险高，采用增量添加策略
- **排产算法升级为运筹优化**：线性规划/遗传算法可获得更优解，但实现复杂度高且需要额外依赖，当前贪心算法足以满足业务需求
